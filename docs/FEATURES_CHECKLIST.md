## What each feature actually does

**F1 – Chat.** Message bubbles, typing indicator, quick-reply chips, suggested
topics derived from recent searches, inline retry after a failed turn, and the
server's safety block surfaced as a badge.

**F2 – Accounts.** Parent registers/signs in (Firebase Auth, or the local demo
session when Firebase is not configured). Multiple child profiles per parent, each
with name, age, avatar, restrictions and output preferences. Profiles can be edited
and deleted.

**F3 – Explainability.** Every card shows title, media type, category, age range,
publication year, summary, matched tags, a `topic` / `discovery` badge and a
plain-language explanation generated by the backend.

**F5 – Dashboard.** Daily (7 days), weekly (8 weeks) and monthly (6 months) views;
totals for searches, recommendations, saves, active days and feedback; a bar chart
of searches per bucket; ranked topic list; thumbs-up ratio.

**F7 – Output customisation.** Number of picks (1–10), summaries vs titles only,
sort by relevance / newest / oldest and a show-explanations toggle. Stored per child
(`PATCH /children/{id}`) and also sent with each `POST /chat` so the very next answer
respects the change.

**F8 – Favourites & feedback.** Optimistic heart toggle with rollback on failure,
thumbs up/down, Saved tab grouped by child, and removal with confirmation-free undo.

**F9 – Admin portal.** Server-rendered Jinja pages with sidebar navigation,
statistics cards, responsive tables, search + filters, pagination, validated forms
and confirm dialogs. All writes go through the backend.

**F10 – External links.** NLB Singapore and Open Library links open with
`Linking.openURL`; failures surface as a toast instead of crashing.

**F12 – Restrictions.** Per-child blocked sensitivity categories and an age-band
depth setting (strict / balanced / explorer). The mobile app only *renders* what the
API returns — filtering is enforced server-side (see the mock's
`mock-api/app/services/recommender.py` for the reference behaviour).

**F13 – Switching.** A horizontal switcher on the Chat, Saved and Insights tabs plus
a full-screen “Who's reading?” screen. The active profile survives app restarts
(AsyncStorage) and drives every request.

**F14 – User management.** Parents, their children, restriction counts and last
activity. Search by e-mail/name and filter families with/without children.
Destructive account operations are intentionally backend-only.

**F15 – Model management.** Deployed version with metrics, version history with
activation, and a retraining request form. Training itself never runs in the browser.

## Mocked / demo-only behaviour

| Area | Reality in this build | What production needs |
| --- | --- | --- |
| Authentication | Works with Firebase when `EXPO_PUBLIC_FIREBASE_*` is set; otherwise a local demo session (`dev:<email>` bearer token) | Point the app at a real Firebase project and set `DEV_AUTH=false` |
| Recommendation engine | Deterministic keyword/tag matcher (`services/recommender.py`) behind the real API contract | Call the trained model service; keep the response shape |
| Retraining | `POST /admin/api/retrain` records a queued job | Worker that consumes jobs and updates `model_versions` |
| Storage | SQLite file; schema is Firestore-shaped | Firestore collections mirroring `parents`, `children`, `catalogue`, `events` |
| Admin accounts | Single configured administrator (`ADMIN_EMAIL`/`ADMIN_PASSWORD`) | Firebase custom claims or an `admins` collection |
| Model metrics | Seeded values in `model_versions` | Metrics written by the training pipeline |
| E-mail flows | Not implemented | Firebase verification / password-reset e-mails |
